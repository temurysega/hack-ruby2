# Умный роутинг выплат

Механизм распределения выплатных операций между платёжными провайдерами- фильтрация допустимых провайдеров, выбор лучшего по комбинации,
каскад при отказе и объяснимость каждого решения.

## Стек

Ruby 3.4, стандартная библиотека (`json`, `csv`, `yaml`). Внешних зависимостей нет,
решение запускается на голом Ruby. RSpec и RuboCop подключены ток для разработки.

## Запуск

Обработать тестовую очередь и собрать сдаваемые файлы

```
ruby bin/route --queue data/operations_queue_test.json --out routing_decisions_test.json
ruby bin/report --decisions routing_decisions_test.json --queue data/operations_queue_test.json --period 2026-07-30
```

Первая команда пишет `routing_decisions_test.json`, вторая `routing_report_test.json`,
обе кладут файл в корень репозитория.

Проверка валидатором на публичной очереди

```
ruby bin/route --queue data/operations_queue_10.json --out out/routing_decisions_10.json
ruby scripts/validate_10.rb out/routing_decisions_10.json
```

## Как принимается решение

1. Hard ограничения отсекают провайдеров, которым заявку отдать нельзя
2. Оставшиеся получают оценку по восьми сигналам, каждый нормализован в 0...1
   и умножен на вес профиля
3. Побеждает наибольшая сумма. При отказе провайдера в приёме заявка уходит
   следующему по рангу, при пустом пуле на self-провайдера
4. В `attempts` попадают все рассмотренные провайдеры с причиной и разбором оценок

## Ограничения

Проверки допуска делятся на два уровня, и это важно для понимания поведения.

**Неснимаемые** приходят из `providers.json`, нарушать нельзя никогда:
статус, диапазон суммы чека, банковский фильтр, маржа, свободные реквизиты,
дневной лимит оборота.

**Симуляционные** наша модель состояния поверх исходного снимка- заявки, занятые в работе, зарезервированный дневной бюджет, интенсивность
в заявках за минуту.

Автопроверка организаторов судит о допустимости по статическому снимку
`providers.json` и симуляционного состояния не видит. Поэтому если наши
симуляционные ограничения отсекли всех внешних провайдеров, роутер повторяет
отбор по исходному снимку и только после этого уходит на self-провайдера.
Дневной лимит при этом не ослабляется никогда. Такие решения помечены
причиной `relaxed_internal_limits`.

Провайдеротсекается по первому сработавшему правилу, поэтому перестановка двух строк
меняет причину отказа. Порядок скопирован из `scripts/validate_10.rb`
и покрыт тестом на эквивалентность.


## Как расширять

**Провайдер** дописать объект в `providers.json`, при необходимости добавить
его в `overrides`. Имён провайдеров в коде нет.

**Правило допуска**  метод в `constraints.rb` и его имя в списке `RULES`.
Место в списке определяет приоритет причины отказа.

**Сигнал** метод в `scoring.rb`, имя в списке `SIGNALS`, вес в профилях
`strategy.yml`.

## Стратегии

Стратегия выбирается флагом `--profile`, веса лежат в `config/strategy.yml`
и меняются без правки кода.

```
ruby bin/route --queue data/operations_queue_10.json --profile aware
```

профили и что учитывают: 
`balanced`  все факторы вместе, работает по умолчанию 
`split`  долю по количеству заявок
`volume`  долю по объёму в рублях 
`cascade`  очередь по `priority` 
`bands` | диапазон суммы чека 
`conversion` | фактическую успешность провайдера 
`aware` текущую загрузку и дефицитность 
`commitments` обязательный дневной оборот 

### Восемь сигналов

`conv`  с какой вероятностью выплата пройдёт 
`cnts` недобрал ли провайдер свою долю по количеству
`voll` недобрал ли по деньгам
`prio`  какая у него позиция в каскаде
`band`- подходит ли он под эту сумму 
`load` сколько осталось запаса до лимитов 
`keep` не тратим ли дефицитного провайдера впустую 
`turn` набран ли обязательный оборот по договору 

побеждает наибольшая сумма. Чистая стратегия ставит единицу нужному сигналу и нули
остальным, `balanced` смешивает все восемь.

Конверсия считается не по заявленной `conversion_24h`, а смесью заявленного
с фактическим из `operations_history.csv` со сглаживанием редких выборок.
