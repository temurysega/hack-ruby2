# Умный роутинг выплат

Механизм распределения выплатных операций между платёжными провайдерами- фильтрация допустимых провайдеров, выбор лучшего по комбинации,
каскад при отказе и объяснимость каждого решения.

## Стек

Ruby 3.1 и новее, стандартная библиотека (`json`, `csv`, `yaml`). Внешних зависимостей нет,
решение запускается на голом Ruby. RSpec и RuboCop подключены только для разработки.

## Запуск

Обработать тестовую очередь и собрать сдаваемые файлы

```
ruby bin/route --queue data/operations_queue_test.json --out routing_decisions_test.json
ruby bin/report --decisions routing_decisions_test.json --queue data/operations_queue_test.json --period 2026-07-30
```

Первая команда пишет `routing_decisions_test.json`, вторая `routing_report_test.json`,
обе кладут файл в корень репозитория.

Проверка валидатором на публичной очереди

```
ruby bin/route --queue data/operations_queue_10.json --out out/routing_decisions_10.json
ruby scripts/validate_10.rb out/routing_decisions_10.json
```

Валидатор организаторов зашит под заявки `op_101`-`op_110`, поэтому сдаваемый файл
проверяется обобщённой версией, которой очередь передаётся вторым аргументом

```
ruby scripts/validate.rb routing_decisions_test.json data/operations_queue_test.json
```

## Тесты

```
bundle install
bundle exec rspec
```

85 примеров в четырёх файлах: `constraints_spec` 24, `reporter_spec` 23, `scoring_spec` 21,
`router_spec` 17. Среди них эквивалентность hard-фильтра функции организаторов на случайных
входах, накопительная проверка порядка правил, нормализация сигналов скоринга и сквозной
прогон роутера, результат которого скармливается настоящему `scripts/validate_10.rb`.

Стиль проверяется отдельно, замечаний быть не должно

```
bundle exec rubocop
```

## Как принимается решение

1. Hard ограничения отсекают провайдеров, которым заявку отдать нельзя
2. Оставшиеся получают оценку по восьми сигналам, каждый нормализован в 0...1
   и умножен на вес профиля
3. Побеждает наибольшая сумма. При отказе провайдера в приёме заявка уходит
   следующему по рангу, при пустом пуле на self-провайдера
4. В `attempts` попадают все рассмотренные провайдеры с причиной и разбором оценок

## Ограничения

Проверки допуска делятся на два уровня, и это важно для понимания поведения.

**Неснимаемые** приходят из `providers.json`, нарушать нельзя никогда:
статус, сумма, банк, маржа, дневной лимит
  

**симуляционные** заявки в работе, израсходованные реквизиты, бюджет, интенсивность

Автопроверка организаторов судит о допустимости по статическому снимку
`providers.json` и симуляционного состояния не видит. Поэтому если наши
симуляционные ограничения отсекли всех внешних провайдеров, роутер повторяет
отбор по исходному снимку и только после этого уходит на self-провайдера.
Дневной лимит при этом не ослабляется никогда. Такие решения помечены
причиной `relaxed_internal_limits`, а если в ослабленном пуле кто-то ещё и отказал,
то `relaxed_after_decline`.

Провайдер отсекается по первому сработавшему правилу, поэтому перестановка двух строк
меняет причину отказа. Порядок скопирован из `scripts/validate_10.rb`
и покрыт тестом на эквивалентность.

Имена методов в `RULES` идут в том же порядке, в каком правила применяются.

| метод | что проверяет | код причины |
|---|---|---|
| `stat` | `status` равен `active` | `provider_inactive` |
| `traf` | `traffic_percentage` задан и больше нуля | `traffic_disabled` |
| `amin` | сумма не ниже `limit_amount_min` | `amount_below_minimum` |
| `amax` | сумма не выше `limit_amount_max` | `amount_exceeds_limit` |
| `dyly` | одобренное за сутки плюс зарезервированное плюс эта заявка не пробивают `daily_amount_limit` | `daily_limit_exceeded` |
| `ipct` | заявок в работе меньше `in_progress_count_limit` | `in_progress_count_exceeded` |
| `ipam` | сумма в работе плюс эта заявка не выше `in_progress_amount_limit` | `in_progress_amount_exceeded` |
| `reqs` | остались свободные реквизиты | `no_available_requisites` |
| `marg` | маржа провайдера не выше мерчанта, либо разрешён минус | `negative_margin` |
| `bnks` | банк заявки проходит по списку `banks` с учётом `exclude_banks` | `bank_not_in_list`, `bank_excluded` |
| `rate` | запросов за минуту меньше лимита интенсивности | `rate_limit_exceeded` |


## Как расширять

**Провайдер** дописать объект в `providers.json`, при необходимости добавить
его в `overrides`. В коде нет имён провайдеров, кроме метки self-провайдера
`SELFPROVIDER` в `models/provider.rb`.

**Правило допуска**  метод в `constraints.rb` и его имя в списке `RULES`.
Место в списке определяет приоритет причины отказа.

**Сигнал** метод в `scoring.rb`, имя в списке `SIGNALS`, вес в профилях
`strategy.yml`.

## Стратегии

Стратегия выбирается флагом `--profile`, веса лежат в `config/strategy.yml`
и меняются без правки кода.

```
ruby bin/route --queue data/operations_queue_10.json --profile aware
```

профили и что учитываю: 
`balanced`  все факторы вместе, работает по умолчанию 
`split`  долю по количеству заявок
`volume`  долю по объёму в рублях 
`cascade`  очередь по `priority` 
`bands` диапазон суммы чека 
`conversion` фактическую успешность провайдера 
`aware` текущую загрузку и дефицитность 
`commitments` обязательный дневной оборот 

### Восемь сигналов

Каждый возвращает число от 0 до 1, побеждает наибольшая взвешенная сумма. Чистая стратегия
ставит единицу нужному сигналу и нули остальным, `balanced` смешивает все восемь.

| метод | вес в `balanced` | что означает |
|---|---|---|
| `conv` | 0.26 | с какой вероятностью выплата пройдёт: заявленная `conversion_24h` смешана с фактом из истории по связке провайдер-банк |
| `cnts` | 0.16 | насколько провайдер недобрал долю по количеству заявок против `traffic_percentage`, перенормированного на живой пул |
| `voll` | 0.08 | то же по деньгам, цель берётся из `volume_share_pct` |
| `prio` | 0.06 | место в каскаде по полю `priority`, ранг нормализован размером пула |
| `band` | 0.10 | попадает ли сумма в предпочтительный диапазон из `bands`, иначе запас между min и max |
| `load` | 0.12 | минимальный из трёх остатков: по дневному лимиту, по числу заявок в работе, по сумме в работе |
| `keep` | 0.12 | не тратим ли впустую дефицитного провайдера, для которого ближайшие заявки безальтернативны |
| `turn` | 0.10 | набран ли `daily_turnover_min` и не пробит ли `daily_turnover_max` |

### Остальные короткие имена

| файл | метод | что делает |
|---|---|---|
| `constraints.rb` | `deny` `pass` `scan` | причина отказа одному, список прошедших, разбор всех |
| `scoring.rb` | `calc` `pick` `dcsv` | оценка одного, выбор победителя, решающий сигнал против второго места |
| `scoring.rb` | `shr` `room` `head` `clip` | доля цели в живом пуле, запас по диапазону сумм, запас до лимита, обрезка в 0...1 |
| `router.rb` | `one` `tick` `fall` `scar` `over?` | одна заявка, время заявки из `created_at` либо синтетическим шагом, self-провайдер как запасной, дефицитность в горизонте, пробьёт ли дневной лимит |
| `simulator.rb` | `take?` `res` `late` `rndom` | примет ли заявку, исход, задержка, детерминированный псевдослучай от `operation_id` |
| `history.rb` | `conv` `bank` `expr` `late` `stat` | сглаженная конверсия, она же по банку, доля просрочек, средняя задержка, сводка |
| `reporter.rb` | `unrc` `hard?` `sole?` `obs` | недостижимые цели, отсекло ли жёстким правилом, единственный ли допустимый, число операций в истории |
| `provider.rb` | `hold` `fin` `num` `own?` | занять ресурсы под заявку, освободить по исходу, числовое поле, self-провайдер ли |

Конверсия считается не по заявленной `conversion_24h`, а смесью заявленного
с фактическим из `operations_history.csv` со сглаживанием редких выборок.
